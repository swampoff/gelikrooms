# ЮKassa, подготовленная серверная интеграция v5

**Статус: код сервера и админ-панель готовы к интеграционному тестированию. Реальный магазин не подключён.**

Это самостоятельный backend-адаптер на FastAPI + SQLite в `server/app.py`, а не изменение существующего backend сайта gelikrooms.ru. Он **не импортирует** автоматически данные из `localStorage`, не создаёт платежи без серверной брони, не хранит банковские реквизиты. Сейчас административный доступ по Bearer-токену демонстрационный; в production нужен настоящий серверный логин, роли и короткоживущие сессии. Логи аудита в SQLite не являются полной финансовой отчётностью.

## Модель платежа

1. Администратор создаёт/сохраняет бронь на защищённом сервере бронирований. В хранилище платежного адаптера должны появиться `booking_id`, утвержденная стоимость, e-mail получателя чека и описание услуги. В текущем варианте демонстрационный импорт возможен только при явном `GELIKROOMS_ALLOW_DEMO_IMPORT=true` на изолированном тестовом сервере. В production отключить.
2. Авторизованный оператор вызывает `POST /api/admin/payments/checkout` с **ID существующей серверной брони**, без суммы из браузера. Сервер вычисляет непогашенный остаток из собственной базы, создаёт платёж через `POST https://api.yookassa.ru/v3/payments` с HTTP Basic Auth и сохраненным до запроса ключом `Idempotence-Key`.
3. Из ответа берётся `confirmation.confirmation_url`, которую можно скопировать и передать гостю. Она открывает защищенный платежный интерфейс ЮKassa (Redirect).
4. На HTTPS адрес `/api/webhooks/yookassa` приходят `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture`, `refund.succeeded`. Обработчик проверяет исходный адрес по официальным диапазонам ЮKassa (свою инфраструктуру reverse-proxy необходимо настроить корректно), а затем повторно запрашивает сущность **напрямую у ЮKassa** и сверяет её с локальной суммой, ID и связанной бронью. Одного webhook или возвращения браузера недостаточно для признания оплаты.
5. Для возврата оператор вызывает `POST /api/admin/payments/{payment_id}/refund` с суммой. Сервер предварительно проверяет статус и оставшуюся доступную сумму и регистрирует возврат с идемпотентностью. Лимиты возвратов и конкретные ограничения определяет ЮKassa.
6. Статус фискального чека (`receipt_registration`) записывается, но полная фискализация, формирование чека зачёта предоплаты после проживания и сверка с бухгалтерией **ещё требуют настройки**. Нельзя запускать реальный магазин, не согласовав налоговый режим, НДС и чековые реквизиты.

## Переменные окружения

Используйте `server/.env.example` как перечень ключей. Пример не содержит реальных секретов. Значения храните в secret manager, не в репозитории.

- `GELIKROOMS_ADMIN_API_TOKEN`: длинный случайный ключ для тестового админ-соединения, минимум 24 символа.
- `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`: данные **тестового магазина** ЮKassa; секрет доступен только серверу.
- `GELIKROOMS_RETURN_URL`: HTTPS адрес возврата, принадлежащий вашему домену. Не считать посещение этого адреса подтверждением оплаты.
- `GELIKROOMS_RECEIPT_VAT_CODE`: код НДС из настроек вашей кассы. **Не выставляйте по догадке.** С 2026 года у ЮKassa для 22% и 22/122 имеются коды 11 и 12 соответственно, но это не означает, что вам нужна именно эта ставка.
- `GELIKROOMS_RECEIPT_PAYMENT_MODE`, `GELIKROOMS_RECEIPT_PAYMENT_SUBJECT`: тип расчета и услуги по вашей схеме работы.
- `GELIKROOMS_DB`: файл SQLite в недоступной из web области.
- `GELIKROOMS_ALLOW_DEMO_IMPORT`: `false` в production, `true` только в изолированной тестовой среде.

## Установка тестового сервера

```bash
cd gelikrooms-admin/server
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
# Установите секреты в окружении (НЕ в Git) по шаблону .env.example
uvicorn app:app --host 127.0.0.1 --port 9000
```

Статический фронтенд запустите отдельно (`python3 -m http.server 5173`) или через веб-сервер. Для работы панели с backend настройте обратное проксирование `/api/*` того же домена на FastAPI. В production нужен HTTPS, WAF/rate limit, защищенная сессия оператора, мониторинг, журнал аудита и резервирование БД.

В аккаунте ЮKassa в разделе `Интеграция / HTTP-уведомления` настройте webhook `https://<ваш-домен>/api/webhooks/yookassa` и события оплаты/возврата. Нужен порт 443 или 8443, HTTPS. Прокси не должен принимать поддельные `X-Forwarded-For`; приложение сверяет `request.client.host`. Если reverse proxy расположен перед приложением, проверьте, какой IP попадает в `request.client.host`, и ограничьте запросы на edge.

## API текущей версии

| HTTP | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/health` | Флаги настройки, без секретов |
| GET | `/api/admin/summary` | Брони, операции и статусы ЮKassa; Bearer |
| POST | `/api/admin/bookings/demo` | Загрузить одну тестовую бронь; только если разрешено отдельным флагом |
| POST | `/api/admin/payments/checkout` | Создать Redirect-платёж, сумма вычисляется на сервере |
| POST | `/api/admin/payments/{id}/reconcile` | Сверить платёж с ЮKassa |
| POST | `/api/admin/payments/{id}/refund` | Инициировать возврат после проверки |
| POST | `/api/webhooks/yookassa` | Получить уведомление, проверить источник и повторно запросить статус |

### Безопасность и ограничения

- Не собирайте номера карт, CVC и пароли на стороне GelikRooms.
- Все реальные денежные действия должны выполняться через **тестовый** магазин до окончательного запуска. Код не совершал сетевых запросов к ЮKassa при тестировании.
- Сервер имеет таблицы `payment_intents` и `refund_intents`: ключ идемпотентности сохраняется **до** запроса к провайдеру и повторно используется при тайм-ауте.
- Вебхуки не могут сами пометить оплату успешной: только подтверждённый ответ API ЮKassa меняет статус.
- Для настоящего запуска нужны единые транзакции броней и финансов, защита от двойного бронирования на сервере, аудит действий сотрудников, резервные копии и обработка персональных данных по применимому законодательству.
- Статусы из локального деможурнала `db.payments` **не синхронизированы** с реальной ЮKassa. Они остаются отдельно в разделе «Финансы».
- Веб-приложение использует временный токен оператора только в оперативной памяти вкладки. Для production заменить на HttpOnly Secure SameSite-cookie, CSRF-защиту и ролевую модель. Не применять тестовый токен для общедоступного магазина.
- Настоящие интеграции с PMS, CRS, Booking, Суточно и другими каналами требуют отдельной настройки, как и фискализация при зачёте аванса.

## Тесты

```bash
cd gelikrooms-admin/server
pytest -q test_app.py
```

Тестовый провайдер имитирует ответы ЮKassa: авторизация, создание и повторное создание ссылки, платёж `pending/succeeded`, невозможность возврата до подтверждения, ограничения по сумме, поддельный webhook, серверная сверка, подтверждённый возврат, тайм-аут и повтор с прежним ключом. **Ни один тест не списывает деньги.**
